Follow one complete cycle

  1. src/main.cpp enters app::init(), then app::run().
  2. The loop samples pH and EC and pushes a timestamped snapshot into history.
  3. The FSM receives a Tick with current readings and readiness flags.
  4. The display and serial telemetry present values, status and state.
  5. The scheduler calls the timer HAL, which yields with vTaskDelay().

Use the pattern when adding a feature

Place a new sensor's peripheral operations in the HAL, its voltage-to-unit conversion in a driver, and its use in decisions or reporting in the application. The scheduler calls the timer HAL directly because it has no separate device-specific conversion.

The boundaries are conventions: all firmware sources are explicitly registered in one ESP-IDF component in main/CMakeLists.txt. Namespaces and header interfaces organize the code; not every module is a class.

Timing: this is a sequential loop running in a FreeRTOS task. Its cycle time is approximately work time + the configured 1,000 ms delay, with scheduling/tick effects. Display work delays the next sample. A dedicated fast safety task and fixed-period scheduling are not implemented.
Exercise: trace a pH reading from app::run() to the ADC and back.
Expected: the manager coordinates sampling, the HAL acquires voltage, and the pH driver converts voltage to pH.

02 · Control logic

Guarded finite-state machine

A finite-state machine (FSM) gives the controller one explicit operating state. An event requests a transition; guards decide whether it is allowed; output callbacks perform the actions.

From / eventCondition and actionResult
INIT / initializeConfirm outputs off and pumps readyIDLE, or FAULT on failure
IDLE / StartAll guards pass; power off; start pumpsPRIME
PRIME / FlowConfirmedGuards pass, before timeout; enable powerRUNNING
PRIME or RUNNING / StopPower off, then stop pumpsTransient STOPPING → IDLE
Active operation / lost readinessAttempt shutdown and record reasonLatched FAULT
FAULT / ResetReadiness restored and shutdown succeedsINIT; initialize again

Understand the startup guards

start_blocker() returns the first failed check: external fault; pump availability and callbacks; nonzero saved duties; verified flows; fresh sensor data; available and calibrated pH, EC and turbidity; available and closed interlocks; and a power callback.

A sample needs a nonzero sequence and a timestamp no later than now. Age greater than 3,000 ms is stale. Priming times out at 60,000 ms, including a FlowConfirmed event arriving at that deadline.

How to extend the FSM

  1. Define the event, allowed source states, guard and output action before changing code.
  2. Return a specific reason when rejecting a transition or latching a fault.
  3. Keep output sequencing explicit: shutdown attempts power-off first, then pump-stop even if power-off fails.
  4. Add host cases for acceptance, rejection, callback failure and timing boundaries.
STOP attempts shutdown in any state, but does not clear a latched FAULT or bypass INIT. A shutdown failure becomes ShutdownFailed. These are software shutdown attempts, not physical confirmation that equipment stopped.
Exercise: with otherwise healthy host inputs, advance now_ms to 3,001 ms after the sample timestamp and send Tick while RUNNING.
Expected: FAULT with StaleSensors; power-off and pump-stop are attempted. Keep synthetic readiness in host tests only.

03 · Actuator control

PWM and coordinated
pump control

Pulse-width modulation (PWM) changes the fraction of each period for which an output is high. Three ESP32 LEDC channels share a 10 kHz, 10-bit timer. The pump manager stores operating duties; the driver and HAL apply outputs.

Period = 1 / 10,000 Hz = 100 microseconds
Duty steps = 2^10 = 1,024
Hardware duty = round(percent × 1,024 / 100)
90% → 922 steps → approximately 90.04% high time
PumpGPIOTarget flowSaved duty
Inlet470 mL/min90%, one measured operating point
Outlet 1549 mL/min65%, measured
Outlet 2621 mL/min42%, measured

Separate configuration from actuation

  1. init() loads saved settings but configures physical outputs at zero.
  2. set_operating_duty() saves a valid 0–100% value for a later start. Saving it does not start a pump.
  3. start_all() requires every saved duty to be finite, valid and nonzero before issuing channel writes.
  4. Channel writes occur in order. A write failure triggers driver shutdown attempts and makes the manager unavailable for further starts.
  5. stop_all() remains callable after faults so shutdown can be attempted again.

set_manual_duty() applies an output immediately and is a lower-level API. Direct pump calls do not enforce all reactor FSM guards. Normal reactor sequencing belongs through the FSM; operator commands are not yet wired to a physical interface.

Flow is not duty: 49 mL/min does not mean 49% PWM. The 70 mL/min inlet measurement at 90% is one operating point, not a linear model. Outlet 1 was measured at 49 mL/min with 65% duty. Outlet 2 was measured at 21 mL/min with 42% duty. Combined flow verification is still pending. This is open-loop duty control; it has no PID flow regulator.

Practice with fake hardware

Use pump_control_test.cpp to simulate successful setup, partial startup and stop failures. Check initial zero outputs, rejection of invalid duties, and shutdown attempts on every configured channel after a write failure.

Exercise: keep one outlet's saved duty at zero and call start_all() in a host test.
Expected: rejection before any pump starts. Then inject a failure during a valid coordinated start and check shutdown attempts.

ADC sampling
and noise reduction

The analog-to-digital converter (ADC) measures sensor voltages. The shared ADC1 HAL configures 12-bit one-shot reads with 12 dB attenuation and creates an ESP-IDF curve-fitting calibration handle for each used channel.

Implement the acquisition sequence

  1. Resolve the GPIO to an ADC1 channel; reject unsupported mappings.
  2. Create or reuse the shared ADC unit and channel calibration.
  3. Acquire 32 raw samples. If any acquisition fails, return an error.
  4. Mark the block clipped if any raw sample is ≤ 0 or ≥ 4,090.
  5. Calculate the integer mean and convert it using ADC calibration.
  6. Return the raw mean, millivolts and clipping flag to the sensor driver.
// Simplified outline; SDK error handling omitted here.
int sum = 0;
bool clipped = false;
for (unsigned i = 0; i < 32; ++i) {
    const int raw = read_one_raw_sample(); // illustrative helper
    clipped |= raw <= 0 || raw >= 4090;
    sum += raw;
}
const int mean = sum / 32;
// Use the ADC calibration API to obtain millivolts.

Why average a block?

A mean reduces random sample noise. For independent, zero-mean noise, the standard deviation of the mean scales approximately as 1/√N: 32 samples can reduce it by about 5.7 times. Correlated noise, offset and sensor calibration errors do not follow that improvement.

This is a fresh block average for each read, not a moving window across application cycles. Checking clipping before averaging prevents one saturated sample from disappearing inside an acceptable-looking mean.

Two calibrations: ADC calibration maps raw counts to pin voltage. Sensor calibration maps board voltage to pH or EC. A calibrated ADC does not mean the probe has been calibrated. Missing ADC calibration is an initialization failure.
Exercise: consider 31 raw readings of 2,000 and one of 4,095.
Expected: integer mean = 2,065, but clipped = true. The sensor driver rejects the reading despite its plausible mean.

05 · Conversion algorithms

Calibration, compensation
and hysteresis

pH: a line through two reference points

The pH driver uses voltages measured in pH 7 and pH 4 buffers. Its default estimates are 1,500 mV and 2,032.44 mV, with calibrated = false.

pH = 7 + 3 × (V − V7) / (V7 − V4)
V = 1,766.22 mV, V7 = 1,500 mV, V4 = 2,032.44 mV
pH = 7 + 3 × 266.22 / (−532.44) = 5.50

Measure stable reference voltages, populate PhCalibration, then call sensor_manager::set_ph_calibration() and check its return value. The driver accepts V7 strictly between 1,322 and 1,678 mV, and V4 strictly between 1,854 and 2,210 mV. These windows prevent a zero or reversed slope. Output must be finite and in pH 0–14. No pH temperature compensation is implemented.

EC: divider correction and temperature normalization

The EC input uses a 10 kΩ / 20 kΩ divider, so board voltage is pin voltage × 1.5. The driver converts to conductivity and normalizes to 25 °C using a manually supplied liquid temperature.

Vboard = Vpin × 1.5
raw_EC = Vboard_mV / 164
EC25 = raw_EC × K / [1 + 0.0185 × (T − 25)]

At Vpin = 154.488 mV, K = 1 and T = 25 °C:
Vboard = 231.732 mV → EC25 = 1.413 mS/cm
At the same voltage and T = 30 °C: EC25 ≈ 1.293 mS/cm

Determine each correction factor from stable readings in the low and high standards: K = reference_EC25 × [1 + 0.0185 × (T − 25)] / raw_EC, using the reference value at 25 °C. Apply both through set_ec_calibration(); each must be strictly between 0.5 and 1.5. set_ec_temperature() accepts 0–40 °C. Settings are RAM-only.

Hysteresis: avoid rapid range switching

The previous range's factor gives a pre-compensation estimate. Above 2.5 mS/cm, choose the high factor; below 2.0 mS/cm, choose the low factor; between the thresholds, keep the current range. Use the chosen factor for EC25. The boundaries themselves do not force a switch.

Exercise: start in low range with both factors equal to 1; feed raw EC values 2.4 → 2.6 → 2.3 → 1.9.
Expected: low → high → high → low. Default coefficients still produce NeedsCalibration, even when values look reasonable.

Explicit errors
and circular storage

A reading contains a value and its status. Raw counts and pin/board voltages help diagnostics. Unavailable values default to NaN; each record adds monotonic uptime and a sequence number.

StatusMeaningConsumer behavior
NotInitializedSensor is not readyShow unavailable
AdcErrorAcquisition failedShow unavailable
VoltageOutOfRange / ValueOutOfRangeInput or converted value is invalidShow an error; reject for control
NeedsCalibrationFinite estimate availableDisplay with warning; FSM rejects
OkValid calibrated readingEligible for control if also fresh

Preserve fresh failures

Construct a fresh result on every read. Store failures just like successes; never replace them with an older good value. effective_status() also rejects nonfinite or negative values that incorrectly claim Ok or NeedsCalibration. Serial and TFT consumers use shared validity helpers.

Store history in a fixed-size ring

Store owns 60 records. The next write index wraps around at capacity, replacing the oldest record. Insertion and age lookup take constant time and require no heap allocation in the store.

// Core indexing used by Store:
records_[next_] = {sensors, sampled_at_ms, ++sequence_};
next_ = (next_ + 1) % capacity;
if (count_ < capacity) ++count_;

// age = 0 means latest; first reject age >= count_.
index = (next_ + capacity - 1 - age) % capacity;

latest() and newest() copy the selected record out, so callers do not hold references to slots that the next write might overwrite. An out-of-range lookup clears the output and returns false.

History is RAM-only and clears on reboot. Sixty records are roughly one minute at the current cadence, not an exact time window. The store and FSM assume one calling task; concurrent consumers need an ownership or synchronization design.
Exercise: push 65 records into an empty store, keeping record 65 as an ADC failure.
Expected: size 60; newest sequence 65; oldest retained sequence 6; latest status is the failure, not record 64's valid value.

07 · Testable hardware boundaries

Dependency injection
and deterministic simulation

Dependency injection supplies an operation from outside the code that uses it. The FSM accepts three function pointers, allowing identical state logic to control real outputs or test doubles.

// Host-only illustration; no physical hardware is accessed.
bool pumps_on = false;
bool power_on = false;
bool fake_start() { pumps_on = true; return true; }
bool fake_stop() { pumps_on = false; return true; }
bool fake_power(bool on) { power_on = on; return true; }

app::state_machine::Machine machine(
    {fake_start, fake_stop, fake_power});
machine.initialize(true); // Confirms off, then enters IDLE.

The production adapter injects real pump callbacks but a null power callback, which blocks START. Host fixtures inject all callbacks and controlled readiness inputs to exercise the full sequence.

A second seam: link-time HAL replacement

Host executables compile real application and driver code with fake implementations of HAL functions. Their CMake targets omit the real peripheral implementations. The same interface is preserved without a virtual class hierarchy.

  1. Define repeatable sensor inputs and a virtual clock.
  2. Record output calls and their order; simulate success or failure.
  3. Advance virtual time in fake acquisition, display and delay operations.
  4. Assert recovery, stale-value rejection and shutdown behavior.

Run the existing tests from the repository root

cmake -S src/test -B build/host-tests
cmake --build build/host-tests
ctest --test-dir build/host-tests --output-on-failure
ctest --test-dir build/host-tests -R '^fsm_' -V
ctest --test-dir build/host-tests -R '^simulation_' -V

The current CMake file registers 42 cases across FSM, pumps, sensors, display/storage and simulation. Each integration scenario runs 90 application cycles, captures serial output and TFT pixels, and keeps pumps at zero. Generated traces and captures live under build/host-tests/simulation/.

Virtual delays are test inputs. The simulation does not emulate FreeRTOS, establish real-time deadlines, validate wiring, or model reactor chemistry. The count above describes registered tests; generating this guide is not a fresh test run.

Display strips
and DMA synchronization

The TFT path separates formatting, drawing and transfer. The display manager prepares text and status tones; the TFT driver draws glyphs; the LCD HAL sends RGB565 pixels over SPI to the ST7789 panel.

Render a strip instead of a full framebuffer

The screen is 240 × 240 pixels with two bytes per pixel. One 240 × 24 strip uses 11,520 bytes (11.25 KiB), compared with 115,200 bytes (112.5 KiB) for a full framebuffer. Ten strips cover the display.

The renderer reuses a static strip to avoid placing that workspace on the task stack. The HAL owns a separate DMA-capable strip. Together these two pixel buffers use 22.5 KiB, plus other objects and SDK resources. The whole firmware is not allocation-free: LCD setup allocates DMA memory and a semaphore.

Respect buffer ownership during transfer

  1. Clear and render a text row in the reusable pixel workspace.
  2. Copy it into the HAL's DMA-capable buffer.
  3. Submit the strip with esp_lcd_panel_draw_bitmap().
  4. The transfer-completion interrupt signals a FreeRTOS semaphore.
  5. The task waits for that signal before reusing the DMA buffer.
Renderer → copy → DMA buffer → SPI transfer
                                  ↓ completion interrupt
Next strip ← task resumes ← semaphore signal

The wait has a configured 250 ms timeout. On failure, the display is disabled. After a timeout, the HAL retains its DMA buffer and semaphore because the peripheral may still reference them. Further display writes stop while monitoring continues.

DMA does not make this loop nonblocking. Hardware transfers are asynchronous internally, but the caller waits for each strip. A slow panel still extends the interval between samples. The panel is enabled after the first complete frame.

Expected: telemetry reports the failure, later display writes cease, and sensor sampling continues through cycle 89.

Defensive configuration
and feature extension

Defensive programming validates inputs where they enter a subsystem. Shared configuration expresses board-wide rules; drivers check device constraints; the HAL checks peripheral capabilities and SDK errors.

BoundaryExisting validation
Shared pin ownershipDistinct pH/EC pins; no sensor/display/pump conflicts
Display configurationDistinct permitted pins and vertical offset 0–80
Pump commandsValid index; finite duty within 0–100%; readiness
Sensor conversionClipping, finite voltages, physical output ranges
Hardware operationsESP-IDF return codes; supported ADC/GPIO mapping
FSM inputFresh calibrated readings and hardware readiness

Why use more than one check?

A pin can support ADC operation yet already belong to a pump. A finite sensor value can lie outside the device's supported range. A valid calibrated sample can be too old for control. Each layer checks the information it owns.

Extension exercise: a future turbidity sensor

  1. Confirm the sensor model, electrical interface and calibration method. Existing turbidity files are scaffolds, not working acquisition code.
  2. Add configuration and pin-ownership checks for that interface.
  3. Implement peripheral access in the HAL and physical-unit conversion in the driver. Return an explicit status on failure.
  4. Sample through the application and populate Snapshot::turbidity. Keep an uncalibrated estimate visibly marked.
  5. Register implementations in main/CMakeLists.txt and host targets.
  6. Test valid input, initialization failure, bad values, calibration status, display formatting and FSM rejection.

Turbidity already participates in FSM readiness checks. Implementing its acquisition removes only one blocker; flow, interlock, calibration and power-control requirements still apply.

Separate measurements and derived values. The planned EC-based theoretical-pH result belongs in the application layer as a separate field. It must not overwrite electrode-measured pH or live in the EC hardware driver. No such calculation currently exists.
Exercise: configure pH to use GPIO4 in a host pin-conflict test.
Expected: shared validation rejects it before ADC setup because GPIO4 is assigned to a pump.

10 · Put the techniques into practice

Practice workflow
and source map

A small, repeatable learning cycle

  1. Trace: choose a behavior, such as a failed pH read. Follow it through driver, manager, stored record, display and FSM.
  2. Predict: write down the expected value/status, state, output calls and visible message.
  3. Simulate: supply the input or failure in a host fixture. Change one condition at a time.
  4. Verify: compare the result with your prediction and inspect the first failed assertion or trace entry.
  5. Extend: make a small change in the owning layer, add a behavioral test, then rerun the relevant suite.

Build board firmware after host verification

Activate the installed ESP-IDF environment, then use the isolated ESP32-S3 N16R8 configuration:

idf.py -B build/esp32s3 \
  -D IDF_TARGET=esp32s3 \
  -D SDKCONFIG=build/esp32s3/sdkconfig \
  -D SDKCONFIG_DEFAULTS=sdkconfig.defaults.esp32s3 build

This command builds firmware only. Hardware testing is separate. Host success does not prove physical ADC accuracy, pump flow, interlock response, SPI timing or watchdog behavior.
